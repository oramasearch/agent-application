# agent-application v0.1.0

**Released 2026-10-17. The first release.** One Python service, the **Application Agent**, and one
private image, `docker.io/oramasearch/agent-application:v0.1.0`. Proprietary to Orama; private
repository and image.

The Application Agent builds web apps and data apps for a person from a description, and deploys
them as lake Apps only after that person confirms. A first turn reads the workspace facts it needs
(datasets, their schemas, governed SQL, Services, repositories, existing Apps), asks the model for a
complete App (every source file plus an `app.toml`), validates it, and returns it as a proposal with
no repository or App writes. A later turn that carries the reviewed proposal back commits the files
to a private lake repository, creates or updates the App, builds an image first when the App needs
packages outside app-runtime's baked set, deploys it, and follows the rollout to Ready. Lake's
Ship → Apps page and Ask Orama's app delegate are its callers.

This release is the same tree as commit `3a38da8`, which every Lake already runs (see
[Where it runs](#where-it-runs)), plus these notes, the release test, and `version` in `/healthz`.

How it works in more detail: [service and bus operation](../operations/service.md),
[building, confirming and deploying Apps](../building/apps.md), [evaluation scenarios](../evals/scenarios.md).

## What it includes

### The HTTP API (port `PORT`, default 8080)

| Route | What it does |
|---|---|
| `GET /healthz` | `{ok, agent: "agent-application", version, model, prompt_version}`. The operator's liveness and readiness path |
| `POST /v1/turn` | One turn. With `AGENT_SERVICE_TOKEN` set, requires `Authorization: Bearer <token>`, otherwise `401`. A body that is not JSON is `400`; an answer with `ok: false` is `422`; any other path is `404` |

A turn's request body:

| Field | Meaning |
|---|---|
| `message` | What the person asked (required) |
| `lake_token` | The person's delegated lake credential for this turn (required); on the bus, the task credential lake hands over at claim |
| `lake_url` | Lake's address (required, or `LAKE_URL`) |
| `customer_id` | The account; attached to every customer-scoped read and to every write |
| `conversation_id` | Continues a conversation held in this process; a new one is made when absent |
| `context.confirmed_proposal` | The reviewed proposal, sent back to deploy it. Without it, a turn only designs |

The answer is `{ok, conversation_id, trace_id, reply, result}`, where `result` is
`{kind, files, app, confirm}` and `kind` is:

- `question`: one focused question, or an explanation that the proposal could not be validated
  or a build failed (`confirm: false`);
- `proposal`: the full file set and the App description (name, mode, repository, path, framework,
  port, host, auth, bindings, env), `confirm: true`;
- `deployed`: the confirmed App, its repository, revision and rollout; `reply` gives its URL, or why
  the rollout failed or did not reach Ready within three minutes.

### The lake agent bus

When `LAKE_URL` and `AGENT_BUS_TOKEN` are set, the service also starts one background worker that
takes turns from lake's agent bus under the name `AGENT_BUS_AGENT` (default `agent-application`).
The code (`lake_bus.py`) does exactly this:

1. Long-polls lake's `receive_agent_tasks {agent, from_sequence, wait_ms: 10000}` (`GET`), starting
   at sequence 1 each time the process starts and continuing from `next_sequence`. The bus topic is
   `agent-tasks.agent-application` on lake's Zetta and carries task ids only, never content.
2. For each task id, calls `claim_agent_task {task_id, agent}`. A `conflict` or `not_found` (another
   replica or attempt has it) is skipped. The claim answers the task body, with the task credential
   in place as `lake_token`.
3. Runs the turn on a pool of four threads: publishes one `progress` event (*Building the App
   proposal*), runs the same turn as `POST /v1/turn`, then publishes `result` with the whole answer,
   or `failed` with the error, through `publish_agent_event`.
4. On a receive failure, logs it and retries after two seconds.

The bus token reaches only those three bus capabilities. The agent renews no lease itself: lake
renews a claim's lease on every capability call made with that task's credential, which the turn
makes as it reads and builds. Lake gives Application Agent tasks the kind `app`; the agent does not
check the kind. If the bus is not configured, the service logs `not configured` and serves HTTP only.

### What it calls on lake

All calls are `<lake_url>/v1/<capability>` with the turn's credential: reads as `GET` with the
arguments as query parameters, writes as `POST` with a JSON body.

**Reads the model may make while designing** (the one model tool, `lake_read`, with a fixed allow
list; anything else is refused before a request is made): `list_datasets`, `get_dataset`,
`workspace_sql`, `list_services`, `list_repositories`, `repository_tree`, `repository_file`,
`list_apps`, `get_app`, `app_logs`, `build_logs`, `get_build`, `receive_app_events`,
`receive_build_events`. `customer_id` is added to `app_logs`, `build_logs`, `get_app`, `get_build`,
`list_apps`, `list_datasets`, `list_repositories`, `list_services`, `receive_app_events`,
`receive_build_events` and `workspace_sql`.

**Calls the service makes itself on a confirmed turn**, in order:

| Step | Capabilities |
|---|---|
| Find or create the private source repository (reused by exact name within the customer) | `list_repositories`, `create_repository` (`visibility: private`) |
| Commit the files under the App's path | `commit_repository_files` |
| Find or create the App (reused by exact name within the customer) | `list_apps`, `create_app` (always `mode: runtime` with the source) |
| Only when the manifest needs packages outside the baked set: build, wait up to 15 minutes, and on failure report the last 20 log lines | `build_app` (with the source), `receive_build_events`, `get_build`, `build_logs` |
| Deploy the source revision, or the built image reference | `deploy_app` |
| Follow the rollout up to three minutes; a non-Ready state counts only if it holds at the deadline | `receive_app_events`, `get_app`, and `app_logs` to explain a failure |

Lake grants a confirmed turn's credential `create_repository`, `commit_repository_files`,
`create_app`, `build_app`, `get_build` and `deploy_app` only when `agent_turn` verified the
confirmation against the stored proposal (lake#561).

### The model

- Every model call goes to lake's model gateway, `<lake_url>/openai/v1`, with the turn's own
  credential as the API key (lake#248). Lake counts the tokens against the turn's workspace and
  enforces the account's model-token limit. The service holds no provider key.
- Chat Completions with JSON output, up to 10 tool rounds per answer and up to 2 repair rounds in
  which the validation failures are sent back to the model.
- Model: `APPLICATION_AGENT_MODEL`, default `gpt-5.5`.
- **Prompt version `v1`** (`PROMPT_VERSION` in `service.py` and `agent.py`; the prompt is
  `src/agent_application/prompts/v1.md`). Every trace records it.

### What a proposal must pass (in the code, on both turns)

- Frameworks `fastapi`, `streamlit` or `static`; mode `runtime` or `image`; port 1–65535; auth
  `lake` (default) or `public`. `public` is refused on a design turn unless the person's message
  asks for public or anonymous access; on a confirmed turn lake's confirmation decides.
- `app.toml` and `README.md` are required; at most 40 files and 900 KiB; no absolute or `..` paths;
  no duplicate paths; every `.py` file must compile.
- No secret in source, manifest or env: likely secret literals, the turn's own credential, and
  credentials inside dependency URLs are refused; an env name that looks secret must be a reference
  `{"secret": "<name>"}` (but see [known issue 3](#known-issues)).
- `app.toml`'s name, framework, port and bindings must match the proposal.
- Dependencies outside the baked set (`fastapi`, `httpx`, `jinja2`, `numpy`, `pandas`, `plotly`,
  `pydantic`, `streamlit`, `uvicorn`) require image mode in the proposal; on confirmation the
  service derives `APP_DEPS` from them and discards any `APP_DEPS` the proposal set.
- Defaults filled in: `mode: runtime`, `port: 8080`, `auth: lake`, no bindings, empty env.

### The image

`docker.io/oramasearch/agent-application`, **private** on Docker Hub.

- Two stages on `python:3.12-slim`: the build stage copies `uv` 0.11.7 from
  `ghcr.io/astral-sh/uv:0.11.7` and runs `uv sync --frozen --no-dev --no-editable`; the runtime
  stage copies only the virtual environment.
- Runs as UID `10001` (user `agent`), exposes 8080, entrypoint `agent-application-serve`.
- No named build contexts: it builds from the repository alone.
- The development dependency `orama-app-runtime` (pinned from git at `692faac`) is used only by the
  tests and is not in the image.

### How lake reaches it

- The Orama operator runs it as a **library agent** for every Lake: one Deployment and one Service
  on port 8080, probed on `/healthz`, non-root with a read-only root filesystem and a writable
  `/tmp`, no Kubernetes token. It sets `LAKE_URL`, `PORT`, `TRACE_DIR=/tmp/traces`,
  `AGENT_SERVICE_TOKEN`, `AGENT_BUS_TOKEN` (from `lake-<name>-agent-bus`, this agent's key only) and
  `AGENT_BUS_AGENT=agent-application`.
- Lake learns its address from `LAKE_AGENT_ENDPOINTS` (`agent-application=<url>`, set by the
  operator); a Lake without that entry answers that the Application Agent is not running.
- Lake dispatches turns as tasks over the agent bus (above) and never waits on the agent inside an
  HTTP request.

## What it does not include

- **Conversation memory that survives the process.** A conversation's history is held in memory
  in one replica; a restart, or a turn that reaches another replica, starts it again. The agent
  does not read the `prior_turn` lake puts in a turn's body.
- **Workspace scoping of its own.** It passes no `workspace_id`; lake derives the workspace from the
  task credential (issue 3 below).
- **Creating secrets.** It never asks for or stores a secret value; a secret reaches an App only
  through a binding or a reference.
- **Frameworks other than FastAPI, Streamlit and static sites**, and building images itself (lake
  builds them).
- **Idle backoff on the bus.** The worker polls again as soon as a receive returns.
- **A live eval result in this release.** The evals need a live model and were not run.

## Known issues

Security-relevant first.

1. **Turn traces hold workspace content outside the workspace Zetta.** Every turn writes the
   person's message and the whole answer (the generated source) as JSON to `TRACE_DIR` on the pod's
   `/tmp`, kept until the pod is replaced. The org rule is that workspace data lives in the
   workspace Zetta. [agent-application#21](https://github.com/oramasearch/agent-application/issues/21).
2. **`POST /v1/turn` is unauthenticated when `AGENT_SERVICE_TOKEN` is unset.** The operator always
   sets it; a hand-run service without it accepts any caller (who still needs a valid lake
   credential to do anything). [agent-application#23](https://github.com/oramasearch/agent-application/issues/23).
3. **Secret references in a proposal use the old form, which lake now refuses**
   ([agent-application#19](https://github.com/oramasearch/agent-application/issues/19)): the prompt
   and the validator propose `{"secret": "<name>"}`, and lake's `create_app` answers
   `invalid_input`, so an App that needs a secret environment variable cannot be created by the
   agent.
4. **A repository with the same name in another workspace makes the deploy fail with a conflict**
   ([agent-application#18](https://github.com/oramasearch/agent-application/issues/18)):
   `ensure_repository` matches by name and customer, not workspace.
5. **No explicit workspace IDs, and no idle backoff on the bus**
   ([agent-application#3](https://github.com/oramasearch/agent-application/issues/3)): calls rely on
   the task credential for the workspace, and the receive loop does not hold to at most one empty
   receive per minute.
6. **The Lake's agent model setting does not reach this agent.** The operator sets `AGENT_MODEL`
   from `spec.agents.model`; the agent reads `APPLICATION_AGENT_MODEL`, so it always uses its
   default `gpt-5.5`. [agent-application#22](https://github.com/oramasearch/agent-application/issues/22).
7. **The model is offered reads a design turn cannot make.** `lake_read` lists `build_logs`,
   `get_build` and `receive_build_events`, which lake grants only on a confirmed turn; on a design
   turn they come back as errors to the model.
8. **Conversation history is never evicted** from the process's memory.
